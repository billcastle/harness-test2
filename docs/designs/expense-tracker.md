# Design: Personal Expense Tracker (single-user web app)

Generated by /office-hours on 2026-11-11

## Problem Statement
One person wants to see what they spend: each expense and totals, for the current month (default view), a chosen month, a year, all time, or a custom date range, with a summary and graphs. Expenses have categories. Entries come from manual add/edit or from uploaded PDF statements (BPI, GCash, Maribank; samples in `./statements`). The UI must be a no-brainer for adding and editing. Single user, deployed to a subdomain, gated by a 4-digit PIN.

## Constraints
- One user, one PIN, personal use. Deployed to a subdomain over HTTPS.
- User asked for simple tech and implementation (see Open Questions: the chosen approach is heavier than "simple").
- Currency PHP, timezone Asia/Manila. Store amounts as integer centavos.
- Goal stated for this session: learning / vibe coding.

## Premises (confirmed)
1. PDF import is the real project. One parser per bank, and every import shows a preview where categories can be fixed and rows unticked before anything is saved. No silent saves.
2. Statements contain non-expenses (self-transfers, time-deposit placements, interest, incoming money). These are imported as `transfer`/`income`/`ignored` and unticked by default so totals reflect real spending. Refunds are imported as `kind=refund`, ticked by default, and reduce net spending (see Aggregation rules).
3. Re-imports and overlapping statements must not double-count (dedupe on date + amount + description + source, surfaced in the preview).
4. The PIN is a real gate: 4 digits is 10,000 combinations, so server-side check with lockout/backoff, HTTPS, no PIN logic in the client.

## What the sample statements showed (evidence: text extraction via macOS PDFKit, pages 1-2 only)
- GCash: columns come out interleaved (dates, descriptions, amounts on shifted lines; some rows lack a description). Needs coordinate-based extraction, not line splitting.
- Maribank: plain text loses which column an amount is in (OUTGOING vs INCOMING). Direction must come from x-position or from the running balance. Has "Others" rows and 100,000.00 time-deposit placements that are not spending.
- BPI: text is character-spaced; page 2 returned no text (may be image-based). Not yet verified whether it is a credit-card or deposit statement.
- Only the first 1-2 pages of each file were read. Remaining pages are unverified.

## Approaches Considered
- A: Python + SQLite + server-rendered pages (htmx, Chart.js, pdfplumber). Recommended; rejected by the user in favor of B.
- C: Parse PDFs in the browser with pdf.js, thin server. Not chosen: harder to test parsers.
- B (chosen): see below.

## Recommended Approach (user's choice: B)
TypeScript SPA + API + Postgres.
- Frontend: React SPA with a bar chart (by category) and a line chart (over time). Pages: Dashboard (default = current month), Transactions (inline-editable table with a quick-add row), Import (upload, preview, confirm), PIN screen.
- Dashboard: date-range control (This month default, Last month, This year, All time, Custom). Total, count, by-category breakdown, spend over time (daily within a month, monthly within a year). Dates are calendar dates in Asia/Manila; ranges are inclusive of both ends; the column type is `date`.
- Aggregation rules: `amount_centavos` is always positive and `kind` carries direction. Dashboard total, count, category and trend figures sum `kind=expense` only, minus `kind=refund` rows (refunds reduce net spending in their category). `income`, `transfer` and `ignored` are excluded. `kind` is editable inline in the Transactions table and in the import preview, so a wrong auto-classification can be fixed.
- Backend: Node API (Fastify), Postgres.
- Data model: `transactions(id, date, amount_centavos, description, category_id, source[manual|bpi|gcash|maribank], kind[expense|income|refund|transfer|ignored], import_batch_id, dedupe_hash NULLABLE indexed (not unique), created_at)`, `categories(id, name, color)`, `import_batches(id, source, imported_at)`, `merchant_rules(merchant_normalized, category_id, updated_at)`.
- Dedupe: for imported rows only, `dedupe_hash = sha256(source | date | amount | normalized description | occurrence_index)`, where normalization lowercases and collapses whitespace and `occurrence_index` numbers identical rows within one statement (two real same-day identical purchases stay distinct). On import, a row whose hash already exists is flagged "possible duplicate" and is unticked by default in the preview; the user can tick it to override. Not a DB uniqueness constraint, so nothing is silently dropped and a batch insert never fails on a repeat. Manual entries have a null hash and never participate.
- Merchant rules: exact match on the normalized description; when a row's category is changed, ask "remember for next imports?"; the most recently updated rule wins. Success criterion below covers it.
- Import flow: upload, detect bank (auto, with a manual override dropdown), parse to rows, mark duplicates and likely non-expenses, preview with editable category and kind and a tick box per row, confirm to save as one batch.
- Import failure handling: only `.pdf`, max 10 MB. A password-protected or unreadable file is rejected with a clear message (password entry not supported in v1). Rows or pages that cannot be parsed are shown in the preview as error rows with the raw text, never silently omitted; the user can fix or skip them. The uploaded PDF is discarded after parsing and never stored (only the parsed rows are kept).
- Undo batch: deletes every row of that batch, including ones edited after import, behind a confirm showing the count. Merchant rules learned from that batch are kept.
- Auth: PIN stored hashed (argon2) in server config, checked server-side only. Failed attempts are counted per client IP: delays of 1 min after 5 failures, then 5, 15 and 60 min (cap 60 min), reset on a successful login; plus a global cap of 30 failures in a rolling hour across all IPs that returns a generic "try later" and rejects even a correct PIN while active. That denial of service against the owner is an accepted tradeoff (it only lasts until the rolling hour clears). Client IP source: Caddy overwrites `X-Forwarded-For` with the real peer address, Fastify `trustProxy` trusts only the Caddy hop on the compose network, and the app port is not published outside that network; otherwise every request would look like it came from Caddy and the per-IP counter would collapse into a global one. Session: httpOnly + Secure + SameSite=Strict cookie, 30-day sliding expiry, Logout button. CSRF: SameSite=Strict plus an Origin header check on all state-changing requests. HTTPS required.
- Deploy: one small VPS, docker compose (app + Postgres) behind Caddy for automatic HTTPS on the subdomain. An automated daily `pg_dump` (cron) is kept 14 days on the host and pushed off-host by `rclone` to a storage bucket of your choice (destination to be picked at deploy time). Restore steps are written in the README. The owner's job is to check the backups exist and do one restore drill after first deploy.
- Wireframe: none (visual design deferred to /plan-design-review).

## Success Criteria
- Opening the app shows this month's total, category breakdown and trend graph with no clicks.
- Adding an expense takes under 10 seconds; editing an amount or category is one click, inline.
- GCash and Maribank sample statements import with every row correctly dated, amounted and classified, checked row-by-row against the PDF (not just the totals). BPI meets the same bar if the spike shows its text is extractable; if BPI is image-based, the fallback is: BPI is unsupported in v1 (manual entry only), and OCR becomes a separate follow-up decision.
- Re-uploading the same statement adds zero ticked rows (all rows flagged as possible duplicates, unticked).
- Wrong PIN 5 times from one IP blocks that IP for 1 minute, escalating to a 60-minute cap; a correct PIN resets the counter.
- Changing a category offers to remember it; the next import of the same merchant string pre-fills that category.
- Parsing failure never hides data: unparsed rows appear as error rows in the preview.

## UI Specification (added by /autoplan design review)
- Layout and navigation: top bar with the app name, one global date-range control, tabs (Dashboard, Transactions, Import, Categories) and a Logout item in the top-right menu. The range control is shared by Dashboard and Transactions and lives in the URL (`?from=&to=`); default is This month. Custom range is a two-date picker (inclusive end, start must not be after end).
- Dashboard hierarchy: 1) net total, largest element, with the range label directly above it (for example "November 2026"); 2) trend line; 3) category bar chart (colors from `categories.color`, label text always shown); transaction count is a small secondary label; a "View transactions" link carries the same range. Trend granularity: daily when the range is 62 days or less, otherwise monthly. Amounts use PHP formatting (₱1,234.50). A negative net (refunds exceed spending) shows a minus sign and the label "net of refunds".
- Transactions: default sort date descending, search on description, category filter, server-side pagination of 50 rows. Columns: Date, Description, Category, Amount; a `kind` badge shows only when kind is not `expense`. Edit pattern: click a cell to edit in place, Enter saves, Esc cancels; a failed save reverts the cell and shows an error message. Refunds show as a negative amount in a distinct color plus a "Refund" badge. Delete asks for confirmation and offers a 5-second Undo.
- Quick-add: always-visible row at the top of Transactions on desktop, a bottom sheet on mobile. Tab order: Amount, Category (typeahead, defaults to last used), Description, Date (defaults to today in Asia/Manila). Amount accepts "250.50". Enter saves, highlights the new row briefly, and returns focus to Amount for rapid entry.
- Mobile-first: below 640px, transactions render as list rows (description, category, amount) and tapping a row opens an edit sheet; at 640px and above they render as the inline-editable table.
- Import preview: upload shows a progress state with Cancel. The preview has a sticky summary bar ("48 rows, 41 will import, 5 duplicates, 2 errors, net ₱X") whose Confirm button states the count it will save. Row order: error rows first, then normal rows, then duplicates and non-expenses collapsed. A duplicate row shows a "possible duplicate" badge with a link to the existing row. A "needs category" counter shows rows still uncategorized. Per-row category has an inline "Remember" checkbox, default on (this replaces the per-change prompt in the Merchant rules bullet), plus a bulk "apply to similar rows" action. Refund rows take their category from merchant rules or manual selection. After Confirm, redirect to Transactions filtered to that batch with a toast. An Import history list on the Import page holds the Undo action. An unsupported or undetected bank shows a clear message with a link to manual entry. If the session expires mid-preview, the preview stays in client memory and returns after PIN re-entry.
- Categories page: add, rename, recolor, delete. A default system category "Uncategorized" always exists, appears in charts and is where imported rows with no rule match land. Deleting a category reassigns its transactions to Uncategorized. A merchant-rules list lets you delete a wrong rule.
- PIN screen: four numeric boxes (`inputmode=numeric`), auto-submit on the fourth digit, a text error for a wrong PIN (not color-only), a lockout countdown ("Try again in 4:32"), and a generic "try later" message for the global cap. Failed attempts rejected while the global cap is active do not extend its window. Encrypted backups: dumps are encrypted before leaving the host (rclone crypt or equivalent) and the destination bucket is private.
- State coverage (loading / empty / error):
  - Dashboard: chart skeletons / empty state with two buttons "Add expense" and "Import statement" / error banner with Retry.
  - Transactions: row skeletons / "No transactions in this range" with a clear-filters link / inline error banner.
  - Import: parse progress with Cancel / "Choose a statement to start" / error messages per failure type.
  - Quick-add and inline edit: disabled save control while saving / n/a / revert cell and show error.
- Accessibility: charts have a "show as table" toggle; category color is always paired with its name; full keyboard flow for quick-add and inline edit; body text contrast at least 4.5:1; touch targets at least 44px.
- Visual style (taste, provisional): one light palette defined as CSS variables, IBM Plex Sans with tabular numerals for amounts, calm surfaces with minimal chrome and no card mosaics. Dark mode deferred.

## Engineering Specification (added by /autoplan eng review)
- Architecture: `Browser (React SPA) -> Caddy (TLS, 10 MB body cap, security headers) -> Fastify API (default-deny auth middleware) -> Postgres`; PDF parsing runs in a separate worker/child process (and, under spike outcome b, a Python parser service reachable only on the compose network, with no published port, a size limit and a timeout) that returns results to the API.
- Parser contract: `parse(bytes) -> {rows[], errors[], bankDetected, confidence, reconciled}` with one module per bank. Parsing runs in a child process with a timeout (30 s) and memory cap; a crash or timeout returns a parse error, never takes down the API. Each parser reconciles its parsed sum or running balance against the statement's own totals; a failed reconciliation shows a warning in the preview. Unrecognized layouts fail loudly as error rows. Bank classification keywords (transfer/income/ignored heuristics) live in an editable data file, not code.
- Spike evidence bar: before the spike gate closes, collect at least 2 statements per bank (different months), not one.
- Data integrity: `CHECK (amount_centavos > 0)`; `merchant_rules.merchant_normalized` is the primary key and rules are upserted; the dedupe normalization and merchant normalization are one shared function in one module; the "Uncategorized" row is flagged system and cannot be deleted (enforced in the service and by a DB constraint); deleting a category reassigns its transactions and its merchant rules to Uncategorized inside one DB transaction; `transactions.updated_at` records edits (the Undo-batch confirm also shows how many rows were edited since import).
- Dedupe semantics: matching is by hash existence; documented cases (same rows re-imported, overlapping window with different occurrence counts, a row deleted then re-imported) each have a test.
- Idempotent import confirm: the client sends a batch UUID; `import_batches.id` is unique; the whole batch inserts in one DB transaction; a retry or double-click returns the existing batch. The server caps rows per request and re-validates every row (kind, category, amount, date); it never trusts client-supplied classification.
- Time and money: the server computes "today" and "this month" explicitly in Asia/Manila (never bare `new Date()`); the Postgres `date` type is parsed as a string, not a JS Date. Amounts are parsed from strings to integer centavos with no float math; rules are specified for "1,250.5", "250.555" (rejected), negatives and currency symbols (rejected), and a maximum cap. Parsers use the same function.
- Queries: aggregation is done in SQL (`GROUP BY` date/category), with indexes on `(date)` and `(category_id, date)`; list pagination sorts by `date DESC, id DESC`. The category bar chart renders a negative bar when refunds exceed spend in that category (or clamps at zero with a footnote; implementer chooses and tests).
- Auth hardening: sessions are stored server-side (table with a hashed token); the sliding expiry write is throttled to once per hour; cookie uses the `__Host-` prefix; the Origin check rejects state-changing requests with a missing Origin; Caddy sets HSTS, CSP, `X-Content-Type-Options`, `frame-ancestors none` and a Referrer-Policy. Lockout counters live in Postgres and are updated with one atomic upsert before the PIN is compared, so parallel guesses cannot bypass the limit. Owner recovery: `docker compose exec app node reset-pin` resets the lockout counters and sets a new PIN. A lockout activation is written to the log. An integration test asserts the app port is not published and that a spoofed `X-Forwarded-For` from outside does not change the client IP. The PIN hash is a secret (env or docker secret, never in the repo); a 4-digit PIN hash is brute-forceable offline if leaked, so it protects only against casual exposure. A rate limit applies to all API routes, not only login.
- Upload hardening: PDF magic-byte check, `bodyLimit` of 10 MB enforced at Caddy and Fastify, streaming multipart, upload route behind the default-deny auth middleware, parser container non-root with a read-only filesystem, pdf.js `isEvalSupported: false`, dependency pinned. Logs never contain PINs, descriptions or raw PDF text. UI renders descriptions as text only; `dangerouslySetInnerHTML` is banned.
- Data fetching: TanStack Query with invalidation after every edit, delete, undo and import so dashboard totals never go stale. Delete with Undo is a soft delete (`deleted_at`) restored by Undo and purged after 24 hours.
- Migrations: a named migration tool runs on container start; seeding of "Uncategorized" and starter categories is idempotent; a deploy that changes the schema is preceded by a backup.
- Backups: the success ping goes to a dead-man's-switch service (for example healthchecks.io) so a silent failure alerts; a monthly `pg_restore` check into a scratch database; the rclone crypt key is stored separately from the VPS.
- Privacy of fixtures: `statements/` is added to `.gitignore`; test fixtures are sanitized (names, account numbers, phone numbers replaced) hand-verified JSON files.
- Sequencing: auth (step 3) must be complete before the subdomain is ever publicly reachable; steps 2, 4 and 5 may be built and run locally first.
- Test plan (full detail in the eng test-plan artifact): parser golden tests per bank against hand-verified fixtures; dedupe unit tests; money/amount-parsing tests; aggregation tests (expense minus refund, exclusions, empty and refunds-only ranges); API integration tests against a real Postgres in a container; lockout test with a fake clock and a parallel-guess race test; Manila-timezone tests with the clock at 23:30 UTC on a month end; Playwright tests for the quick-add keyboard flow, the inline edit, and the import preview and confirm (including double-click confirm).
